# Database migrations (Drizzle)

The schema lives in [`db/schema.ts`](../db/schema.ts). Migrations are SQL files in `db/migrations/`, generated by Drizzle Kit and applied with `npm run db:migrate`. The database is PostgreSQL on Neon; see the ADRs in [`docs/decisions/`](decisions/).

## Rules

- **Locally, migrations run only against the Neon `dev` branch, as `neondb_owner`** (`MIGRATION_DATABASE_URL` in `.env.local`). `drizzle.config.ts` refuses to run for any other role or branch, and `npm run db:migrate` runs `npm run check:env` first.
- **Never migrate production from this machine** and never put production connection strings in a local file (ADR 0002, "Local env safety"). How production gets its migrations is still to be decided.
- **Never edit a migration that has been applied.** Fix mistakes with a new migration.
- Commit the schema change, the new `.sql` file and the `db/migrations/meta/` changes together.

## How to add a column

1. **Edit the schema.** Add the column to the table in `db/schema.ts`, for example `source: text('source')` on `reservations`.
   - On a table that already has rows, a `NOT NULL` column needs a `default(...)`, or add it as nullable first, fill it, then make it `NOT NULL` in a second migration.
2. **Generate:** `npm run db:generate`. A new file appears in `db/migrations/` (for example `0002_xxx.sql`).
3. **Review the SQL** before applying anything. Look for:
   - `DROP COLUMN` / `DROP TABLE` or type changes (data loss),
   - `NOT NULL` without a default on a table with data,
   - `$1` (a bind parameter) inside `CHECK` or `DEFAULT`: not valid in DDL. Use `sql.raw('...')` for constant literals, as `PHONE_REGEX` does.
4. **Apply:** `npm run db:migrate` (dev branch only). Then check the result, for example with `npm run check:env` and a query as `delta_app`.
5. **Commit** the schema, the SQL and the meta files.

## Things Drizzle cannot generate

Triggers, functions, extensions (such as `btree_gist`) and exclusion constraints are written by hand:

```
npx drizzle-kit generate --custom --name=what_it_does
```

This creates an empty `.sql` file in `db/migrations/`; write the SQL in it. Separate statements with `--> statement-breakpoint`. `0001_updated_at_triggers.sql` is an example.

- **Every new table with an `updated_at` column needs its own trigger.** Add a `CREATE TRIGGER ... EXECUTE FUNCTION set_updated_at()` line in a custom migration (copy it from `0001_updated_at_triggers.sql`).

## Seeding the dev branch (fake data)

`npm run db:seed` puts three fake apartments into the Neon `dev` branch so the app has something to show. The names (`Atlas`, `Berlin`, `Devetka`) match real apartment names from the calendar screen; everything else is made up (`scripts/seed-data.mjs`). It is idempotent: running it again adds nothing.

It can only ever touch `dev`, in layers:
1. It is a manual command in `scripts/`. No install, build or deploy step runs it, and nothing in `api/` imports it.
2. It refuses on Vercel, in CI, with `NODE_ENV=production`, with a `DATABASE_URL` set in the shell, with a role other than `delta_app`, or a branch other than `dev`. Connection details come from `.env.local` only. The role and branch rule is the same one `npm run check:env` uses (`api/_dbGuard.js`).
3. It refuses if `apartments` contains any row not created by the seed (`created_by = 'dev-seed'`), so it cannot add fake rows next to real data.
4. It runs as `delta_app` (insert only), so it cannot delete or change the schema.

The real apartments for production come from the one-time Airtable data migration, not from a seed. Never put real owner phone numbers or addresses in `scripts/seed-data.mjs`. Note that the app reads apartments from Airtable until `api/*` moves to Postgres, so the seeded rows are not visible in the calendar yet.

## Permissions on new tables

Tables created by a migration (as `neondb_owner`) get the default privileges from ADR 0002 automatically: `delta_app` can `SELECT`, `INSERT`, `UPDATE`; `delta_readonly` can `SELECT`; nobody but the owner can `DELETE` or run DDL. Nothing to grant by hand. Objects created by another role would not get them.

## Error codes the API should expect from the schema

| SQLSTATE | Meaning | Typical cause |
|---|---|---|
| `23514` | check constraint | bad phone format, area <= 0, negative amount, check-out before check-in |
| `23505` | unique violation | duplicate apartment `name` |
| `23502` | not null violation | missing `channel` and other required fields |
| `23503` | foreign key violation | unknown `apartment_id` |
| `22P02` | invalid enum value | channel or status outside the allowed list |
| `22012` | division by zero | check-out equal to check-in (the generated `price_per_night_eur` is evaluated before the check constraint, so this code appears instead of `23514`) |
| `23001` | restrict violation | deleting an apartment that has reservations (owner only) |

The API should validate dates and fields first and map these codes to clear 4xx responses.
